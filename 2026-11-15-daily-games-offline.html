    How Daily Games works offline

    How the PWA keeps working with no network

    By Pranav Bakre · Sunday, 15 November 2026

    About Daily Games

    Daily Games is a small web app I built: three daily logic puzzles, Zip, Tango and Sudoku, in plain HTML, CSS and JavaScript. It is served as static files from GitHub Pages, with no backend and no accounts. Puzzles are generated on the device from the date, and times and streaks stay in localStorage. It installs to the home screen and plays with no connection; this lesson is how that last part works, read from its real service worker.

    Play itSource at sw.js v6

    sw.js is a reverse proxy on the phone. On the first visit it saves the app's 15 files (the page under two URLs, its stylesheet and manifest, seven scripts and four icons) into a bucket named daily-games-v6. After that, page loads try the network and fall back to the saved page; every other file comes from the bucket at once and is refreshed in the background. A release reaches phones as a set only when VERSION changes, which swaps in a new proxy with a new bucket and deletes the old one.

    8 min read · 3 events, 25 steps to click, 7 questions

    The three events

    Read sw.js as an nginx in front of the app. Three differences matter, and each shows up below:

    • it only exists after the first visit;
    • the browser starts it per request and may stop it once a response is sent;
    • the browser, not you, decides when a new version replaces it.

    1. First visit: online, no proxy yet

      Online, no proxy yet.

      No. 1 · 7 steps · 3 questions

      The page loads straight from GitHub Pages. After load, it registers the proxy, so the install doesn't compete with the first render.

      navigator.serviceWorker.register('./sw.js')

      The proxy's install handler downloads the 15 files into the bucket. If any one comes back non-2xx, the install fails and the browser retries on a later visit.

      Questions you'd ask

      How big is it?

      About 30 KB over the wire, gzipped: about 100 KB of source plus 15 KB of icons. Zip is the biggest game at 6.2 KB gzipped.

      Why not just rely on the HTTP cache?

      GitHub Pages fixes it at max-age=600 and offers no way to change headers, and the app can't see or control what the HTTP cache keeps. The bucket is the part you control.

      Isn't the index page listed twice?

      Yes. ASSETS lists both './' and './index.html' (sw.js:8–9). Only index.html is ever read back (sw.js:64), so the './' entry is about 1 KB that's never used.

    2. Second visit, offline

      Second visit, offline, from the home-screen icon.

      No. 2 · 10 steps · 2 questions

      Now every request from the page goes through the proxy. Non-GET and cross-site requests pass straight to the network (sw.js:49–52). The rest are routed on one question: is this a page load?

      Offline, the page fetch fails immediately and the saved index.html is served. Every screen is a # route, so that one page covers them all. JS, CSS and icons come from the bucket. Today's puzzle is generated from the date, and streaks come from localStorage['daily-games:v1'] (js/storage.js:3).

      sw.js · lines 55–83, trimmed

      if (request.mode === 'navigate') {  try { fresh = await fetch(request); cache.put(INDEX, …) }  catch { return caches.match(INDEX) }  // offlineif (cached) { fetch(request).then(…); return cached }

      A bar marks the lines the text cites. The rest of 55–83 is trimmed, and … marks code cut from a line.

      Questions you'd ask

      Does it survive a weak signal?

      Not well. Offline, fetch fails fast. On a weak signal it hangs, and nothing times it out, so the app waits for the network before showing the saved page.

      Do the background refreshes always finish?

      No. They aren't wrapped in event.waitUntil, and the browser may stop the proxy once the cached response is sent. Nothing breaks; the bucket just updates less often than it looks.

    3. After a deploy

      VERSION changed from 'v6' to 'v7'.

      No. 3 · 8 steps · 2 questions

      On the next page load, the browser re-downloads sw.js, skipping the HTTP cache for this one file, and compares bytes. Changing 'v6' to 'v7' is the byte change. The new proxy installs next to the running one and fills daily-games-v7; skipWaiting() lets it take over without waiting for open tabs to close. On activate it deletes every other bucket and claims the open tabs.

      sw.js · lines 41–42

      keys.filter(… !== CACHE).map(… caches.delete(key));  // drop v6await self.clients.claim();

      Questions you'd ask

      Don't old service workers pile up?

      No. A site holds at most one worker in each of three slots: installing, waiting and active. Once the new one activates, the old one is discarded; ship v8 while v7 is still waiting and v7 is discarded too. What would pile up is the buckets: discarding a worker doesn't delete its bucket, so without the caches.delete line every release would leave its 15 files behind. At any moment there are at most two buckets.

      Aren't the bump and the background refresh redundant?

      No. The background refresh drifts single files toward the latest, one visit late. The bump replaces all 15 at once as a consistent set. Without a bump, a returning visit gets the new index.html (network first) with the old JS (bucket first), and they only line up a visit later.

    Trade-offs

    1Hand-written proxy, 95 lines

    Instead ofWorkbox, the standard: a build step generates the file list with a hash per file, and only changed files are re-downloaded.

    This costsThe file list and the version bump are manual.

    Workbox costsA build step and a dependency in a repo with neither. Worth it once a forgotten bump costs more than adding the build.

    2Network first for page loads

    Instead ofBucket first for page loads too.

    This costsA weak signal stalls the launch.

    Bucket first costsEvery release shows one load late.

    3Bucket first, background refresh, for files

    Instead ofBucket only, updated by version bumps.

    This costsFiles can mismatch the page for one visit.

    Bucket only costsNever fresher than the last bump.

    4skipWaiting + clients.claim

    Instead ofLet the new version wait and show "Update ready, reload".

    This costsAn open tab switches buckets mid-game.

    Waiting costsUpdate UI, and users who actually reload.

    5localStorage

    Instead ofIndexedDB.

    This costsSynchronous and small; fine for one JSON blob written at most every 250 ms.

    IndexedDB costsAn async API; worth it for many records or blobs.

    Failure modes

    1An error page replaces the saved page

    BreaksThe page-load branch saves any response without checking ok (sw.js:59–61). A mistyped URL under /daily-games/ saves GitHub's 404 as the app.

    DetectLaunching offline shows a 404.

    FixOnly save when fresh.ok.

    2New bucket filled from the HTTP cache

    BreaksaddAll uses normal fetches and Pages sends max-age=600. Within 10 minutes of a visit, the v7 bucket can hold v6 files.

    DetectNew bucket name, old file contents.

    FixFetch with new Request(url, {cache: 'reload'}) in install.

    3Changed a file, forgot the bump

    BreaksPage and JS from different releases for one visit.

    DetectDevTools → Application → Cache Storage still shows the old bucket name.

    FixBump on every change, or let a build step hash the files.

    4Weak signal

    BreaksLaunch hangs on the network-first fetch.

    DetectSlow starts on mobile data.

    FixRace the fetch against a 2–3 s timeout, then serve the bucket.

    5Safari evicts storage

    BreaksIn a Safari tab, WebKit deletes localStorage, the worker and its cache after 7 days of Safari use with no visit to the site. Home-screen apps have their own day counter.

    DetectStreaks reset to zero.

    FixPlay from the home-screen icon, where navigator.storage.persist() may also be granted.

    At scale

    With more releases or contributors, the manual file list and bump become the main source of bugs; a build-generated list with per-file hashes fixes that and stops re-downloading unchanged files. With much more code, save a small shell and let the background branch pick up the rest on first use. Once results must follow the user across devices, localStorage stops being the source of truth: you need accounts and sync, and offline writes become a queue to reconcile.

    Check yourself

    You deploy v7 while someone has had the app open for three days without reloading. When do they get v7?

    On their next page load. Update checks run on page loads, and switching # routes isn't one, so the open tab never fetches the new sw.js. (From web.dev's description of update checks; not tested on this app.)

    You add a "share your time" button that POSTs to a Cloudflare Worker. A user taps it with no signal. What does the proxy do?

    Nothing. It passes non-GET and cross-site requests straight through (sw.js:49–52), so the request fails like on any site and the share is lost unless the page queues it.

    Try it

    1. Desktop Chrome, live site, DevTools → Application → Service workers: sw.js is activated, and Cache Storage shows daily-games-v6 with 15 entries.
    2. Network → Offline → reload. Requests show "(ServiceWorker)" as their source and the app still plays.
    3. Network → "Slow 3G" instead, then reload: the page waits on the network-first fetch.
    4. Locally, set VERSION to 'v7', serve the folder and reload once: daily-games-v6 disappears and daily-games-v7 appears without closing the tab.
